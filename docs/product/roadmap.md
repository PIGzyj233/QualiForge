# QualiForge 路线图

文档状态：MVP 已交付，本文档跟踪 MVP 之后的能力规划。
最后更新：2026-05-26。

## 1. 路线原则

QualiForge 的长期方向是成为团队和 AI Agent 共同使用的测试知识中枢。演进时坚持：

- AI 可以建议、整理、分析，但不能绕过团队治理。
- 正式测试资产必须可追溯、可评审、可回滚。
- 人类看到的是友好的工作流与可视化，系统内部保持结构化实体关系。
- 小团队默认协作，不使用过重权限矩阵。
- 代码仓库分析以只读安全为默认边界；运行代码必须进入更强隔离。
- 私有化部署优先，但架构保留 SaaS 与多 Workspace 演进空间。

## 2. 当前里程碑（近 1~2 个迭代）

聚焦于让 MVP 闭环更稳、更好用。

### 2.1 资产质量与打磨

- 历史用例 AI 导入：识别准确度、字段映射可解释性、批量纠错效率。
- Diff 分析：影响面准确度、推荐回归命中率、模块映射 stale 提醒。
- 测试报告：负责人确认体验、Markdown 导出排版、失败/阻塞聚合视图。
- Agent Workbench：会话恢复、运行取消、staged output 评审 UX。

### 2.2 模块映射闭环（详见 `architecture/module-mapping.md`）

已落地：`keywords / relationship / status / ai_confidence / evidence_refs / repository_id`、AI 模块树草稿。

下一步：

- Repository 静态索引（`repository_id + commit_sha` 维度）。
- AI 映射建议批量产出与冲突预检（primary 冲突、过宽匹配、vendor 排除）。
- Diff 分析使用 `relationship + status` 加权（primary / related / dependency / evidence）。
- 映射规则的导入/导出（YAML/JSON）。

### 2.3 可观测性与成本

- AIInvocationLog 聚合视图与按 Workspace/Project 成本分摊。
- Agent Run 时间线与工具调用瀑布。
- Telemetry：Langfuse 链路与 Prometheus dashboard 模板。

## 3. 中期方向（3~6 个月）

### 3.1 Agent 对外接口

- REST API 查询项目 / 模块 / 正式用例 / 测试计划 / 报告。
- REST API 查询某次 diff 的影响面与测试建议。
- 外部 Agent 提交候选用例进入评审流，调用需审计与限流。
- 评估 MCP Server，让通用 AI 工具直接访问测试资产与 diff 结果。

约束：外部 Agent 不能直接创建正式用例，不能绕过 Workspace 数据策略。

### 3.2 用例版本模型增强

触发条件：团队频繁修改正式用例 / 需要精确证明执行版本。

- 引入显式 `TestCaseVersion`，`TestCase` 保留稳定身份。
- 测试计划显式引用某个正式版本。
- 支持版本对比与回滚；废弃版本仍可被历史计划引用。

### 3.3 评审流程增强

- 多人评审；按模块设置 reviewer；按风险等级要求不同评审人数。
- 评论锚定到步骤、预期结果或字段。
- 评审模板、批量评审、AI 评审质量提示。

复杂流程应可配置；默认体验仍保持轻量。

### 3.4 执行能力增强

- 步骤级执行结果与每步截图/附件。
- 执行计时、重测记录、多轮执行。
- 同一计划下多环境执行；执行人负载分析。
- 失败项自动生成缺陷草稿；失败历史驱动风险等级调整。

### 3.5 报告增强

- PDF 模板与品牌化报告、客户级报告视图、管理层摘要。
- 版本质量趋势、覆盖矩阵、风险热力图。
- 多语言报告、电子签名与确认链。

AI 可生成草稿与风险摘要，结论仍由负责人确认。

### 3.6 第三方工具集成

优先级建议：

1. GitLab Release/MR 回写报告与风险摘要。
2. 缺陷系统链接与缺陷草稿创建。
3. 飞书/Markdown 报告发布。
4. 通知类（飞书/Slack/Teams/企业微信）。
5. Sentry 等错误监控信号回灌 CoverageIndex。

## 4. 远期方向（6 个月以上）

### 4.1 自动化测试与 CI/CD

- 在受控容器中执行白名单命令（单测、接口测试、静态检查）。
- 自动化执行结果合并到测试计划。
- 在 GitLab pipeline 中触发 QualiForge diff 分析。
- 将报告回写到 GitLab Release / MR / Issue。

安全边界：执行必须容器隔离、凭证单独管理、不允许任意命令、产物脱敏。

### 4.2 更强代码理解

- 更完整 AST 分析、函数/类/接口级调用关系、服务间依赖。
- 数据库表/字段、配置变更影响分析。
- OpenAPI / GraphQL / RPC 协议解析。
- 历史 diff 与缺陷、失败用例关联学习。

注意：服务测试决策，不要变成通用代码分析平台。

### 4.3 SaaS 版本

需补齐：租户隔离、计费、配额、Workspace 级存储限制、AI 成本计量、外部 GitLab 授权、凭证加密与密钥轮换、合规声明、可选区域部署。

建议初期仍以私有化为主，SaaS 作为轻量试用入口。

## 5. 暂不做（但保留观察）

- 完整测试管理平台替代 TestRail 的所有能力。
- 面向大型企业的合规审计套件。
- AI 自动操作真实业务系统进行探索测试。
- 完整需求管理 / 缺陷管理 / 代码评审平台。
- 端到端自动化测试编排平台。
- 浏览器自动探索业务系统。

## 6. 决策指标

MVP 发布后优先看以下指标决定下一阶段：

- 团队能否顺利导入历史用例。
- AI 导入后的人工修正成本是否可接受。
- diff 分析是否真的节省了测试负责人判断时间。
- AI 推荐的回归用例命中率。
- AI 候选用例通过评审的比例。
- 测试计划执行录入顺畅度。
- 报告是否能替代人工整理。
- 用户是否要求外部 Agent / MCP / 自动化执行。
