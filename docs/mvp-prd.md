# QualiForge MVP PRD

文档状态：初稿  
日期：2026-05-22  
产品阶段：MVP  

## 1. 产品定位

QualiForge 是一个面向小到中型研发/测试团队的 AI-native 测试资产平台。

它不是传统测试管理工具的简单替代品，而是一个让团队和 AI Agent 都能系统性理解测试资产与代码变更的工作台。平台将 GitLab 仓库、版本 diff、历史测试用例、用例评审状态、测试计划执行结果和测试报告统一成结构化上下文。

第一版优先服务管理混乱的小团队：他们通常已有一些 Excel、CSV、飞书表格、文档或零散平台中的测试用例，但缺少统一治理，也无法让 AI Agent 稳定获得已有用例和代码仓库上下文。

## 2. 核心问题

目标团队的主要痛点：

- 历史测试用例散落在不同文档和表格中，结构不统一。
- 测试用例缺少评审流程，正式用例库质量不可控。
- 发布版本时，测试负责人难以根据 Git tag diff 系统性判断应该测什么。
- AI 生成测试用例时缺少上下文，无法充分利用已有用例、模块知识和代码仓库信息。
- 测试计划执行结果和测试报告依赖人工整理，结论难追溯。
- 小团队不适合复杂权限矩阵和重型企业流程，但仍需要基本治理、审计和可追溯性。

## 3. MVP 目标

MVP 要完成 5 条主闭环：

1. Workspace、项目和 GitLab 仓库接入。
2. Excel/CSV 历史用例 AI 整理导入。
3. 用例库、评审流、状态管理和历史快照。
4. Git tag diff 分析，结合已有用例生成测试建议和候选用例。
5. 测试计划执行录入，生成 Web 在线报告和 Markdown 报告。

MVP 的价值闭环：

旧用例进入平台 -> Git 仓库进入沙盒 -> AI 获得结构化上下文 -> 基于 diff 和已有用例生成建议 -> 人工评审进入正式库 -> 加入测试计划执行 -> 输出报告 -> 执行结果和人工反馈反哺测试资产。

## 4. 非目标

MVP 暂不做：

- 自动化测试执行。
- CI/CD 深度集成。
- Agent 启动项目、运行服务或访问业务数据库。
- 复杂权限矩阵。
- 多人复杂审批流。
- 客户级审计报告、电子签名或合规模板。
- 全量代码语义图谱。
- Elasticsearch 或独立向量数据库。
- Jira、禅道、飞书、Slack 等深度集成。
- MCP Server。
- 公网 SaaS 优先交付。

## 5. 目标用户与权限

### 5.1 PlatformAdmin

平台级管理员，负责：

- 管理整个平台用户和全局配置。
- 配置全局 GitLab 地址白名单或默认 GitLab URL。
- 配置全局 AI 数据策略默认值。
- 管理全局 LLM Provider 和系统级限制。
- 查看平台级审计、任务和成本汇总。

### 5.2 WorkspaceOwner

Workspace 负责人，负责：

- 创建和管理 Workspace。
- 管理成员。
- 管理项目和 GitLab 仓库接入。
- 配置 Workspace 级 GitLab token。
- 配置 Workspace 级模型和 AI 数据策略。
- 配置模块、映射规则和导入策略。
- 确认或调整报告结论。

### 5.3 WorkspaceMember

小团队内默认普通成员拥有较完整的协作能力：

- 创建、编辑草稿用例。
- 提交候选用例评审。
- 评审其他成员提交的用例。
- 管理用例内容和模块归属。
- 创建和执行测试计划。
- 查看测试报告。

默认规则：候选用例至少需要 1 名 WorkspaceMember 通过才能进入正式用例库，提交人默认不能评审自己提交的用例。WorkspaceOwner 可以配置是否允许自评审，以支持个人 Workspace 或极小团队。

## 6. 信息架构

登录后默认进入工作台 Dashboard，而不是项目列表。

顶层导航：

- 工作台：我的待评审、待执行、待确认报告、最近 AI 任务。
- 项目：进入具体项目。
- 用例库：跨项目搜索正式用例和候选用例。
- 评审：集中处理待评审用例。
- 测试计划：查看和执行计划。
- 报告：查看历史报告。
- AI 分析：导入任务、diff 分析、生成记录、成本。
- 设置：Workspace、成员、模型、GitLab、数据策略。

项目内导航：

- 概览。
- 仓库。
- 模块/功能域。
- 用例。
- Diff 分析。
- 测试计划。
- 报告。
- 设置。

UI 风格应为安静、密集、工作台式 SaaS 管理工具。少做营销化大卡片，不把 AI 聊天框作为唯一入口。AI 应作为任务流中的辅助分析能力存在。

## 7. 核心功能需求

### 7.1 Workspace 与项目

- 支持创建 Workspace。
- 支持 Workspace 内创建多个项目。
- 项目归属于 Workspace。
- Workspace 支持成员管理。
- 私有化部署场景下仍保留 Workspace 多租户模型。

### 7.2 GitLab 仓库接入

- WorkspaceOwner 配置 GitLab token。
- token 应为只读权限，至少可读取 repo、tags、commits、diff。
- token 加密存储，不向普通成员展示。
- PlatformAdmin 可配置默认 GitLab URL 或 GitLab 地址白名单。
- 项目可以绑定一个或多个 GitLab 仓库。
- 仓库接入后，平台维护只读 clone/mirror。

### 7.3 Git 沙盒

- MVP 采用私有化部署优先。
- 平台在受控沙盒中维护 Git bare mirror。
- 分析 tag diff 时创建临时 worktree。
- worktree 路径由系统生成，不接受用户传入任意本地路径。
- 不同 Workspace 和 Project 做目录级隔离。
- 禁止符号链接逃逸。
- 支持仓库大小、diff 文件数和任务超时限制。
- MVP 默认不执行项目代码、不启动服务、不运行测试命令、不访问业务数据库。

### 7.4 模块/功能域

- Project 下维护模块/功能域。
- 模块可以是树状或列表结构。
- 用户可手工创建、调整和命名模块。
- AI 可根据历史用例、仓库目录结构、接口路由、README、diff 结果建议模块。
- AI 不自动重构模块体系，最终由人确认。

### 7.5 模块映射规则

每个模块可以关联技术对象和关键词：

- 目录规则，如 `src/order/**`。
- 文件规则，如 `*Payment*`。
- 接口规则，如 `/api/orders/**`。
- 服务规则，如 `order-service`。
- 配置 key 或数据库迁移规则。
- 关键词规则，如订单、支付、退款。

映射来源需要记录：

- 人工配置。
- AI 从仓库推断。
- AI 从历史用例推断。
- 用户从 diff 分析结果中确认。

代码路径、接口、服务、配置等技术关联是系统推断字段，不要求黑盒测试工程师手动填写。

### 7.6 历史用例 AI 导入

支持上传 Excel/CSV。流程：

1. 上传文件。
2. AI 识别表头、字段、合并单元格、多行步骤等结构。
3. AI 转换为平台标准用例草稿。
4. 用户在预览页批量修正和确认。
5. 用户选择提交评审，或由 WorkspaceOwner 批量导入为正式用例。
6. 系统记录原始文件、导入批次、AI 转换结果和人工确认记录。

导入能力应兼容不同团队不统一的表格结构。

### 7.7 用例库与评审

用例状态：

- `draft`：草稿。
- `pending_review`：待评审。
- `approved`：正式用例。
- `rejected`：已驳回。
- `archived`：已归档。

MVP 用例模型采用简化版本：

- `TestCase`：承载当前用例内容和状态。
- `CaseRevision`：记录历史快照。
- `Review`：记录评审过程。
- `PlanItem`：加入测试计划时保存用例快照，避免后续用例修改影响历史计划。

评审操作：

- 通过。
- 驳回。
- 要求修改。
- 评论。
- 编辑候选内容。

通过评审时，当前内容成为正式用例。修改正式用例应产生新 revision，并可根据配置重新进入评审。

### 7.8 用例字段

固定核心字段：

- 标题。
- 模块/功能域。
- 前置条件。
- 步骤。
- 预期结果。
- 优先级。
- 风险等级。
- 标签。
- 需求/缺陷链接。
- 适用版本范围。
- 来源。
- 状态。

系统推断字段：

- 关联代码路径。
- 关联接口/路由。
- 关联服务/组件。
- 关联配置/数据库迁移。
- 关联 diff 分析记录。
- AI 置信度。
- 关联依据。

支持自定义字段：

- 字段名称。
- 是否必填。
- 显示顺序。
- 字段类型。

核心字段语义不允许被团队删除或重定义，以保证 AI、报告和检索稳定工作。

### 7.9 用例内容形态

支持两种形态：

- `structured`：步骤式，包含前置条件、多个步骤、每步操作和预期。
- `free_text`：自由文本，适合导入初期或探索性测试。

正式用例优先标准化为步骤式。WorkspaceOwner 可配置是否允许自由文本用例进入正式库。

### 7.10 Diff 分析

输入：

- Project。
- Repository。
- `baseTag` / `baseRef`。
- `targetTag` / `targetRef`。

分析分三层：

1. 文件级：变更文件、目录、语言、服务/模块归属、变更类型。
2. 文本/结构级：新增/删除/修改的函数、类、接口路由、配置 key、SQL/迁移文件、测试文件等。
3. AI 解释级：基于 diff、仓库上下文、已有用例和模块规则生成影响面、风险点、候选用例和推荐回归范围。

输出：

- 变更摘要。
- 影响模块。
- 风险等级。
- 推荐测试范围。
- 推荐回归用例。
- AI 候选新增用例。
- 变更文件列表。
- 依据和置信度。

Diff 分析页以测试决策优先，而不是以文件列表优先。

### 7.11 AI 测试建议与候选用例

AI 输出分两类：

- 本次版本测试建议：服务当前测试计划，不一定长期保存。
- 可沉淀候选用例：经过评审后进入正式用例库。

AI 候选用例可以直接作为本次计划临时测试项加入测试计划执行，但不能直接进入正式库。若要长期复用，必须提交评审并通过。

所有 AI 输出必须展示：

- 来源 diff。
- 命中的模块映射规则。
- 关联已有用例。
- 关联代码路径/接口/配置。
- 生成理由。
- 置信度。
- 人工反馈入口：确认、忽略、修改。

### 7.12 测试计划

测试计划类型：

- `release`：发布测试。
- `regression`：回归测试。
- `smoke`：冒烟测试。
- `feature`：功能专项测试。
- `custom`：自定义测试。

MVP 主流程重点优化 `release`。

模型简化为：

- `TestPlan`：计划范围、关联版本、负责人、状态、最终结论、报告内容。
- `PlanItem`：单条可执行测试任务。

`PlanItem` 来源：

- 正式用例快照。
- AI 临时建议。
- 手工临时项。

执行状态：

- `not_run`。
- `passed`。
- `failed`。
- `blocked`。
- `skipped`。

MVP 支持整条用例结果和备注，不强制步骤级结果。

### 7.13 测试执行界面

支持两种视图：

- 表格/列表视图：适合负责人查看整体进度、分配执行人、筛选失败/阻塞项。
- 单项执行视图：适合测试人员逐条查看步骤、填写结果、上传证据、链接缺陷。

执行时支持：

- 分配执行人。
- 标记执行状态。
- 填写实际结果。
- 填写失败原因。
- 添加缺陷链接。
- 上传附件或截图。
- 记录执行人和执行时间。

### 7.14 测试报告

MVP 报告主要面向团队内部发布决策，不做客户级审计报告。

报告要回答：

- 这个版本测了什么。
- 什么没有测。
- 失败和阻塞在哪里。
- 风险是否可接受。
- 是否建议发布。

报告结构：

- Summary。
- Version & Diff。
- Scope。
- Execution Statistics。
- Failed / Blocked Items。
- Risk Assessment。
- AI Notes。
- Release Decision。
- Appendix。

AI 可以整理测试事实、总结风险、生成报告草稿和发布建议。最终报告结论必须由负责人确认。

导出优先级：

- Web 在线报告。
- Markdown 导出。
- PDF 后置或通过浏览器打印兜底。

### 7.15 LLM Provider 与模型配置

MVP 支持 OpenAI-compatible API。

配置分两层：

- Provider：API Base URL、API Key、默认 header、组织信息。
- Model Profile：model name、用途、思考等级、最大上下文、最大输出、价格、缓存策略、超时、重试、预算限制。

Model Profile 支持用途区分：

- 导入清洗。
- diff 分析。
- 用例生成。
- 报告总结。

需要记录：

- token 使用量。
- 调用成本。
- 缓存命中。
- 耗时。
- 失败原因。

### 7.16 AI 数据策略

WorkspaceOwner 可以配置 AI 数据策略，默认策略由 PlatformAdmin 设置。

策略分级：

- `ExternalAllowed`：允许发送必要上下文到外部模型。
- `NoSourceCode`：不发送完整源码，只发送 diff 摘要、文件路径、结构信息和用例文本。
- `InternalOnly`：只允许调用内网模型 endpoint。
- `AIDisabled`：禁用 AI 任务，仅保留手工管理能力。

AI 任务开始前必须检查数据策略。

日志只记录输入摘要和数据类型，不记录完整敏感 prompt。

### 7.17 Job 与后台任务

所有耗时工作都作为后台任务执行：

- Git clone/sync。
- tag diff 分析。
- 代码结构索引。
- Excel/CSV 导入解析。
- AI 用例整理。
- AI 候选用例生成。
- 报告草稿生成。
- Markdown 导出。

Job 状态：

- `queued`。
- `running`。
- `succeeded`。
- `failed`。
- `cancelled`。

Job 记录：

- 类型。
- 关联 Workspace/Project。
- 创建人。
- 输入摘要。
- 输出引用。
- 错误摘要。
- 关键日志。
- 开始和结束时间。
- 模型配置。
- token 和成本。
- 缓存命中。

失败任务应支持重试或重新运行。

### 7.18 缓存

缓存分三类：

- Git/代码索引缓存。
- AI 任务结果缓存。
- LLM prompt/semantic cache。

缓存不允许覆盖：

- 人工评审结论。
- 测试执行结果。
- 负责人最终报告结论。
- 权限判断。
- 数据策略判断。

缓存命中需要对用户可见，尤其是 AI 成本相关任务。

### 7.19 审计日志

必须记录影响资产可信度、权限、安全和报告结论的操作：

- 登录/登出、失败登录。
- Workspace 成员增删改。
- GitLab token 配置和更新，不记录 token 明文。
- 仓库接入、同步、删除。
- AI 数据策略变更。
- LLM Provider / Model Profile 配置变更。
- 用例创建、修改、状态变更。
- 用例评审通过、驳回、要求修改。
- 批量导入确认。
- 测试计划创建、范围变更、执行结果变更。
- 缺陷链接添加/修改。
- 报告草稿生成、人工确认、结论修改。
- AI 任务执行摘要和成本。
- 缓存命中和复用关键记录。

MVP 不要求复杂审计查询，但对象详情页应能看到相关历史。

## 8. 技术架构基线

MVP 采用模块化单体，而不是微服务。

技术栈：

- 后端：Python FastAPI。
- 前端：React + TypeScript。
- 数据库：PostgreSQL。
- 队列和缓存：Redis + RQ/Celery/Arq 之一。
- Git/AI Worker：Python 模块内实现。
- 部署：Docker Compose 私有化部署。

基础组件：

- Web 前端。
- Backend API。
- PostgreSQL 主库。
- Redis。
- Background Workers。
- Git Sandbox。
- LLM Provider Adapter。
- Object/File Storage。

PostgreSQL 作为唯一主数据库：

- 主数据。
- JSONB 自定义字段。
- 全文搜索。
- 可选 pgvector。

MVP 不引入 Elasticsearch 或独立向量库。

## 10. MVP 验收标准

MVP 可发布的最低标准：

- 一个 Workspace 可以接入 GitLab 仓库并完成只读同步。
- 一个项目可以上传 Excel/CSV，由 AI 转换为平台用例草稿。
- 用户可以预览、修正、提交评审，并将用例纳入正式库。
- 用户可以配置模块和映射规则。
- 用户可以选择两个 tag 生成 diff 分析。
- diff 分析可以展示影响模块、推荐回归用例、AI 候选用例和依据。
- AI 候选用例可以作为临时测试项加入测试计划，也可以提交评审。
- 测试人员可以执行计划项并录入结果、缺陷链接和附件。
