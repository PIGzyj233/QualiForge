# QualiForge Future Roadmap

文档状态：初稿  
日期：2026-05-22  
用途：记录 MVP 之后要做的事情，避免产品讨论随时间丢失。

## 1. 路线原则

QualiForge 的长期方向是成为团队和 AI Agent 共同使用的测试知识中枢。

演进时应坚持：

- AI 可以建议、整理、分析，但不能绕过团队治理。
- 正式测试资产必须可追溯、可评审、可回滚。
- 人类看到的是友好的工作流和可视化，系统内部保持结构化实体关系。
- 小团队默认协作，不使用过重权限矩阵。
- 代码仓库分析以只读安全为默认边界，运行代码必须进入更强隔离。
- 私有化部署优先，但架构保留 SaaS 和多 Workspace 演进空间。

## 2. MVP 后置能力总览

以下能力不进入 MVP，但应在架构上保留扩展空间：

- 自动化测试执行。
- CI/CD 深度集成。
- MCP Server 和外部 Agent API。
- 更细粒度用例版本模型。
- 步骤级执行结果。
- 多人复杂评审规则。
- 客户级审计报告和 PDF 模板。
- Jira、禅道、飞书、Slack 等协作工具集成。
- 更深入的代码语义图谱。
- 独立向量库或搜索集群。
- 浏览器自动探索业务系统。
- Agent 在沙盒中运行项目测试或服务。
- 公网 SaaS 商业化版本。

## 3. 后续产品方向

### 3.1 Agent 对外接口

MVP 内置 AI Agent，后续应开放结构化接口，让外部 Agent 可以安全读取平台上下文。

可演进能力：

- REST API 查询项目、模块、正式用例、测试计划、报告。
- REST API 查询某次 diff 的影响面和测试建议。
- 外部 Agent 提交候选用例进入评审流。
- 外部 Agent 查询测试计划执行状态。
- MCP Server，用于让通用 AI 工具直接访问测试资产和 diff 分析结果。

原则：

- 外部 Agent 不能直接创建正式用例。
- 外部 Agent 不能绕过 Workspace 数据策略。
- 外部 Agent 的调用需要审计和限流。

### 3.2 自动化测试与 CI/CD

MVP 不执行项目代码。未来可以支持在受控容器中执行白名单命令。

可演进能力：

- 读取 CI 配置，识别测试入口。
- 配置命令白名单。
- 在容器中运行单元测试、接口测试或静态检查。
- 将自动化执行结果合并到测试计划。
- 将失败结果与用例、模块和 diff 分析关联。
- 在 GitLab pipeline 中触发 QualiForge diff 分析。
- 将测试报告回写到 GitLab Release、MR 或 Issue。

安全边界：

- 执行代码必须进入容器隔离。
- 环境变量和凭证需要单独管理。
- 不允许任意命令执行。
- 执行日志和产物需要脱敏策略。

### 3.3 更强代码理解

MVP 做文件级、结构级和 AI 解释级分析。后续可以增强为更稳定的代码知识图谱。

可演进能力：

- 更完整 AST 分析。
- 函数/类/接口级调用关系。
- 服务间依赖关系。
- 数据库表和字段变更影响分析。
- 配置变更影响分析。
- OpenAPI、GraphQL、RPC 协议解析。
- 代码路径到模块的自动学习。
- 历史 diff 与缺陷、失败用例关联。

注意：

- 不应一开始追求完整语义理解。
- 代码理解能力应该服务测试决策，而不是变成通用代码分析平台。

### 3.4 用例版本模型增强

MVP 使用 `TestCase + CaseRevision + PlanItem snapshot` 简化模型。未来当团队需要更严格资产治理时，可以引入显式 `TestCaseVersion`。

可演进能力：

- `TestCase` 保存稳定身份。
- `TestCaseVersion` 保存每个正式版本。
- 测试计划显式引用某个正式版本。
- 用例修改必须产生新版本并重新评审。
- 支持版本对比和回滚。
- 支持废弃某个版本但保留历史计划引用。

触发条件：

- 团队开始频繁修改正式用例。
- 需要审计历史版本。
- 测试报告需要精确证明执行的是哪个版本。

### 3.5 评审流程增强

MVP 为一人通过、提交人默认不能自评审。后续可支持更复杂规则。

可演进能力：

- 多人评审。
- 按模块设置 reviewer。
- 按风险等级要求不同评审人数。
- Owner 强制通过。
- 评论锚定到步骤、预期结果或字段。
- 评审模板。
- 批量评审。
- AI 对评审质量给出提示。

原则：

- 复杂流程应可配置，不应成为小团队默认负担。
- 默认体验仍应保持轻量。

### 3.6 执行能力增强

MVP 只支持整条计划项结果。未来可支持更精细执行。

可演进能力：

- 步骤级执行结果。
- 每步截图/附件。
- 执行计时。
- 重测记录。
- 多轮执行。
- 同一测试计划下多环境执行。
- 执行人负载分析。
- 失败项自动生成缺陷草稿。
- 根据失败历史调整风险等级。

### 3.7 报告增强

MVP 优先 Web 在线报告和 Markdown。未来可以支持更正式的报告体系。

可演进能力：

- PDF 模板。
- 品牌化报告。
- 客户级报告视图。
- 管理层摘要。
- 版本质量趋势。
- 覆盖矩阵。
- 风险热力图。
- 自动生成发布评审材料。
- 多语言报告。
- 电子签名和确认链。

原则：

- AI 可生成草稿和风险摘要。
- 最终结论仍必须由负责人确认。

### 3.8 第三方工具集成

MVP 不做深度集成。未来可按团队最常见工作流逐步接入。

候选集成：

- GitLab Issue / Merge Request / Release。
- Jira。
- 禅道。
- 飞书文档和飞书多维表格。
- Slack / Teams。
- 企业微信。
- Sentry 或其他错误监控。
- OpenAPI 文档平台。

优先级建议：

1. GitLab Release/MR 回写报告和风险摘要。
2. 缺陷系统链接和缺陷草稿创建。
3. 飞书/Markdown 报告发布。
4. 通知类集成。

### 3.9 SaaS 版本

MVP 私有化部署优先。未来可以演进 SaaS，但要注意源码和测试资产敏感性。

SaaS 需要补齐：

- 租户隔离。
- 计费。
- 配额。
- Workspace 级存储限制。
- AI 成本计量。
- 外部 GitLab 授权。
- 更严格的凭证加密和密钥轮换。
- 合规声明和数据处理协议。
- 可选区域部署。

建议：

- 技术上保留多 Workspace。
- 初期商业交付仍以私有化为主。
- SaaS 更适合作为轻量试用和小团队云版。

## 4. 未来可视化方向

MVP UI 以工作台式管理为主。未来可以增强更多可视化，但不能牺牲任务效率。

可视化方向：

- Diff 影响面矩阵：模块 x 风险 x 用例覆盖。
- 用例覆盖地图：功能域、代码路径、历史执行结果。
- 测试计划进度热力图。
- 风险模块趋势。
- AI 置信度和人工确认分布。
- 用例资产健康度。
- 导入批次质量分析。
- 模块映射可信度视图。

原则：

- 先服务测试负责人做决策。
- 文件列表和技术细节是证据，不是主视图。
- 可视化应能下钻到依据。

## 5. AI 能力路线

### 5.1 导入清洗

MVP：

- 识别 Excel/CSV 结构。
- 映射字段。
- 生成标准用例草稿。

未来：

- 自动识别重复用例。
- 合并相似用例。
- 识别低质量用例。
- 自动拆分过大的用例。
- 自动补全前置条件和预期结果。
- 从文档或会议纪要提取测试点。

### 5.2 Diff 分析

MVP：

- tag diff。
- 模块影响。
- 推荐回归用例。
- 候选新增用例。

未来：

- 历史相似变更对比。
- 失败风险预测。
- 缺陷历史关联。
- 需求变更与代码变更对齐。
- 生成测试计划草案。
- 根据执行反馈调整下一次推荐。

### 5.3 评审辅助

MVP：

- 提供生成依据和置信度。

未来：

- 检查用例是否步骤清晰。
- 检查预期结果是否可验证。
- 检查是否重复已有用例。
- 推荐 reviewer。
- 根据模块风险提示缺失场景。

### 5.4 报告辅助

MVP：

- 生成报告草稿和风险摘要。

未来：

- 对比历史版本质量。
- 自动识别发布风险模式。
- 生成管理层摘要。
- 根据失败项生成修复优先级建议。

## 6. 数据与安全后续项

MVP 需要基础数据策略。未来可增强：

- Prompt 脱敏规则。
- 敏感字段识别。
- 源码片段发送审批。
- Workspace 级密钥轮换。
- AI 调用样本审计。
- 数据导出和删除。
- 备份与恢复。
- Git 仓库缓存生命周期策略。
- 更强的 sandbox 隔离。

## 7. 技术后续项

MVP 技术栈为 FastAPI、React、PostgreSQL、Redis、Docker Compose。

未来可根据规模演进：

- pgvector 正式启用。
- 独立搜索服务。
- 独立 worker 集群。
- 对象存储从本地切换到 S3/MinIO。
- Job 取消、暂停、优先级。
- 更细缓存失效策略。
- Worker 并发和限流。
- 更完整 observability。
- 数据库迁移和备份工具链。
- 插件化 LLM Provider。

## 8. 暂不做但保留观察

这些方向暂不进入近期路线，但可以在用户反馈强烈时重新评估：

- 完整测试管理平台替代 TestRail 的所有能力。
- 面向大型企业的合规审计套件。
- AI 自动操作真实业务系统进行探索测试。
- 完整需求管理系统。
- 完整缺陷管理系统。
- 代码评审工具。
- 端到端自动化测试编排平台。
- 面向个人用户的独立轻量版本。

## 9. 后续优先级建议

MVP 发布后优先看这些指标决定下一阶段：

- 团队是否能顺利导入历史用例。
- AI 导入后的人工修正成本是否可接受。
- diff 分析是否真的帮助测试负责人节省判断时间。
- AI 推荐的回归用例命中率。
- AI 候选用例通过评审的比例。
- 测试计划执行录入是否顺手。
- 报告是否能替代人工整理。
- 用户是否要求外部 Agent 或 MCP 接入。
- 用户是否要求 CI/CD 或自动化测试执行。

建议下一阶段优先级：

1. 打磨导入清洗和 diff 分析准确度。
2. 增强报告和发布评审体验。
3. 增加 GitLab MR/Release 回写。
4. 开放 REST API 给外部 Agent。
5. 评估 MCP Server。
6. 评估容器化自动化测试执行。
